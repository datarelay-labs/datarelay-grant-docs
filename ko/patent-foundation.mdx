## 해결하려는 문제

특허 문서는 기존 승인 업무가 대화, 문서 전달, 양식 작성, 자유 형식의 답변 해석 등에 의존하여 비효율적이고 자동화하기 어렵다는 문제에서 출발합니다.

핵심 아이디어는 승인 요청을 구조화된 케이스로 만들고, 사람의 명확한 결정을 자동화의 다음 동작과 연결하는 것입니다.

## 핵심 승인 흐름

1. 사용자 입력 또는 API 요청으로 승인 요청 케이스를 생성합니다.
2. 승인권자에게 이메일로 승인 요청을 전달합니다.
3. 승인권자가 **승인 / 보류 / 거부** 중 하나를 명확하게 선택합니다.
4. 거부되면 요청자 또는 요청을 발생시킨 외부 시스템에 결과를 알립니다.
5. 보류되면 미리 설정된 주기에 따라 승인 리마인드를 전송합니다.
6. 승인되면 선택된 자동화 시나리오 / 플레이북에 해당하는 작업을 실행하거나 실행하도록 연결합니다.

## 이메일을 승인 인터페이스로 사용

특허에는 승인권자가 이메일에 생성된 응답 메뉴를 통해 결과를 선택하는 구조가 설명되어 있습니다. 응답 메뉴는 승인관리 서버, 승인 케이스, 승인 응답, 승인권자 정보와 연결되는 하이퍼링크 방식으로 구성될 수 있습니다.

이 방식은 승인권자에게는 간단한 사용자 경험을 제공하면서도, 시스템 입장에서는 승인 결과를 구조화된 값으로 처리할 수 있게 합니다.

## 템플릿과 승인 요청 생성 지원

특허에는 승인 요청을 만들기 위한 다음 요소도 포함됩니다.

- 승인 케이스 템플릿
- 자동화 시나리오 / 플레이북 목록
- 승인권자 목록
- 요청 정보가 부족할 때 필요한 정보를 안내하는 이메일 응답

DataRelay Grant의 관점에서는 자유 형식의 요청을 단순 전달하는 것이 아니라, 실행 전에 필요한 정보를 명확하게 만드는 원칙으로 이어집니다.

## 모듈 조합형 자동화

자동화는 재사용 가능한 모듈 또는 단위 작업의 조합으로 구성됩니다. 승인된 결과는 미리 정의된 시나리오 / 플레이북과 연결되어 특정 자동화 작업을 수행할 수 있습니다.

## 외부 시스템 API 연동

특허는 별도의 시스템이 API 메시지로 승인관리 서버에 승인 요청을 생성하고, 승인 결과를 다시 API 메시지로 전달받는 구조를 명시합니다.

이 구조가 DataRelay Grant를 DataRelay Link, DataRelay Control 및 다른 외부 시스템에서 공통으로 사용할 수 있는 승인 계층으로 확장할 수 있는 기술적 기반입니다.

## DataRelay Grant에 적용하는 설계 원칙

- **사람의 판단을 명시적으로 기록합니다.** 모호한 문장을 승인으로 추정하지 않습니다.
- **승인과 실행을 분리합니다.** 민감한 자동화는 승인 결과가 확인된 뒤에만 진행합니다.
- **승인 기능을 재사용합니다.** 각 시스템이 자체 승인 기능을 새로 만들지 않고 공통 승인 계층을 호출할 수 있게 하는 방향입니다.
- **자동화를 조합 가능하게 합니다.** 승인 후 실행되는 작업을 재사용 가능한 모듈과 플레이북으로 구성하는 방향입니다.
- **보류를 독립적인 상태로 다룹니다.** 승인도 거부도 아닌 상태를 유지하면서 리마인드와 후속 처리를 수행할 수 있습니다.

## 현재 제품 상태

</Warning>
